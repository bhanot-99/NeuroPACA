Model Stack

BitNet + Ollama

Two layers of compression — architectural (BitNet) and behavioral (graph pruning). Each does something the other cannot.

Layer 1 — Architecture
BitNet b1.58
Every weight in the model is constrained to one of three values: {-1, 0, +1}. At 1.58 bits per parameter this is a fundamental architectural change — matrix multiplications become additions and subtractions. No floating point at inference.
// conventional model
weights: float32 (32 bits/param)
7B model ≈ 28 GB RAM

// BitNet b1.58
weights: {-1, 0, +1} (1.58 bits/param)
7B model ≈ 1.4 GB RAM
runs on CPU · no GPU needed ✓
Layer 2 — Serving
Ollama
Ollama provides the local serving layer — model loading, request routing, context management. It handles the infrastructure so NeuroPACA only talks to a simple HTTP endpoint. The BitNet model runs inside Ollama; the personal graph prunes which heads it actually uses at inference time.
// how they connect
graph.db → score lookup
→ pruning mask built
→ Ollama loads masked model
→ inference on your subnetwork
one HTTP call · zero cloud ✓
Why BitNet matters for NeuroPACA specifically
BitNet solves the hardware constraint — a 7B model that fits in 1.4GB runs on a laptop CPU without thermal throttling. Graph pruning then reduces this further by removing attention heads that are irrelevant to your actual task distribution. These are additive wins: BitNet gives you a small model; your personal graph makes it specifically small for you.

v2 Architecture — Three Upgrades

Giving the System Space
to Think and Act Dynamically

The original 5-manager design was static. These three upgrades make the architecture breathe, dream, and decide on its own.

Upgrade 01 · Inspired by Neurogenesis & Apoptosis
Structural Plasticity — The Architecture That Breathes
Right now all five managers are hard-coded and permanent. This upgrade kills that lock-in. You write a base Node class and let the Event Bus spawn or kill nodes dynamically based on what's actually happening on your machine.
How it works
You start compiling a massive codebase. The system sees CPU at 95% and RAM spiking. It spawns a temporary cluster of Sub-Sensing nodes that only watch thermal limits. When that project ends and those nodes haven't fired for two weeks, the system kills them (apoptosis) — they stop wasting resources. The graph shapes itself around your active projects, not a fixed blueprint.
spawn_node() kill_node() EventBus idle_ttl = 14d
Example lifecycle
// Day 1: heavy Blender render job starts
bus.emit("cpu_spike", 97%) →
  spawn SubSensor("thermal_watch")
  spawn SubSensor("fan_rpm_watch")

// Day 15: render project done,
// nodes haven't fired in 14 days
apoptosis_check() →
  kill SubSensor("thermal_watch")
  kill SubSensor("fan_rpm_watch")
// Architecture is leaner again ✓
Upgrade 02 · Inspired by the Brain's Default Mode Network
Default Mode Network — The System Dreams When You're Away
The original Reminiscence Agent just did database housekeeping during idle time. This upgrade gives the system an imagination. When your CPU drops below 5%, instead of sleeping, it actively thinks — running what-if simulations and generating ideas in the background.
How it works
CPU drops below 5%. The system pulls your highest-score graph nodes — say, a buggy Python script you were stuck on. It uses the lightweight BitNet b1.58 model to autonomously generate potential fixes, alternative approaches, or follow-up queries. These get cached as "idle thoughts." When you return to the terminal, the system doesn't just remember what you did — it has new ideas waiting for you.
cpu < 5% trigger top-K graph nodes BitNet inference idle_cache.db
Example idle session
// You step away. CPU = 2%.
dmn.trigger() →
  nodes = graph.top_k(5)
  // ["buggy_parser.py", "fastapi route", ...]

  for node in nodes:
    thought = bitnet.generate(
      "what-if: " + node.context)
    idle_cache.save(thought)

// You return to terminal:
◆ While you were away, I thought of
  3 approaches for buggy_parser.py ✓
Upgrade 03 · Inspired by Biological Motor Thresholds
Action Gradients — Mathematical Permission, Not Manual Approval
The original W · Action layer was binary: everything required you to approve it. That's not autonomy. This upgrade replaces the gatekeeper with activation thresholds — actions fire when enough pressure accumulates, not when you say so.
How it works — two thresholds
Low threshold (safe actions): Clearing a stale temp cache has a low threshold — a single spike from the Diagnosis node fires it instantly and silently. You never see it happen.

High threshold (dangerous actions): Killing a frozen database process requires synchronized spikes from Sensing + Diagnosis + Learning simultaneously. If that triple pressure isn't met, the system prompts you in the terminal instead of acting.
low_threshold = 1 spike high_threshold = 3 synced spikes pressure accumulator
Threshold examples
// LOW THRESHOLD — fires silently
diagnosis.spike("stale_cache") →
  pressure = 1 ≥ threshold(1)
  action.execute("clear_tmp") ✓

// HIGH THRESHOLD — needs 3-way sync
sensing.spike("db_frozen")
diagnosis.spike("db_frozen")
learning.spike("db_frozen") // missing!
// pressure = 2 < threshold(3)
→ terminal prompt instead:
  "Kill postgres? [y/n]"

Plain English

How the Whole Thing
Actually Works

No jargon. Start here if the diagrams feel overwhelming.

Step 1 — Watching
Your machine is always being quietly observed
Every minute, NeuroPACA logs what's running — which apps, how much CPU they use, what files changed. It doesn't record your screen or keystrokes. Just cold system numbers. This is the X · Sensing layer.
Step 2 — Understanding
Numbers get turned into meaning
Raw CPU spikes don't mean anything alone. The Y · Diagnosis layer correlates them — it learns that "python.exe high CPU at 11pm always means you're running tests before a commit." It starts predicting failures before they happen.
Step 3 — Remembering
A graph grows around your habits
The Z · Learning layer builds a graph database where nodes are your tools, projects, and habits — and edges are the relationships between them. Every node has a relevance_score. Heavy use → score climbs. Neglect → score decays. The graph is literally a map of who you are as a developer.
Step 4 — Acting
It does things — but carefully
Small safe actions fire automatically when pressure builds (clearing caches, pre-fetching docs). Risky actions require more evidence before they execute. If the system isn't confident enough, it asks you in the terminal instead of acting alone.
Step 5 — Dreaming (new)
When you step away, it keeps thinking
When CPU drops below 5% (you walked away, went to lunch), the Default Mode Network fires. It takes your highest-priority graph nodes and uses the local BitNet model to generate ideas — fixes for bugs you were stuck on, alternative approaches, follow-up searches. When you come back, it shows you what it thought about. The architecture that physically changes its shape (Structural Plasticity) means these systems grow and shrink with your workload — nodes spawn when you need them, die when you don't.

Step 01
Graph
Memory

⚠ Problem this creates
Who decides what connects to what? Comparing new data against every node is O(n) and creates noise. No structure means the graph degrades into chaos as it grows.
Step 02
Routing
Layer
10 master nodes + central hub. New data classified first, then placed within the right cluster. Search space shrinks dramatically.
⚠ Problem this creates
Old nodes slowly lose connections. They become orphans. Months-old patterns stop activating and silently disappear. The model drifts toward recency.
Step 03
Reminiscence
Agent
Randomly replays old nodes during idle/sleep. Adjusts relevance_scores. High-score nodes replay often and reinforce their corresponding model weights. Low-score nodes get flagged for pruning.
⚠ Problem this creates
If it runs while you're working, it competes for CPU with actual tasks. And the mapping from graph nodes to model weights needs a bridge — the node concept and the attention head are different things.
Step 04
Scheduled
Training
Training happens during idle/sleep. Sensing runs 24/7 at near-zero cost. Heavy computation happens when you don't care — just like your brain consolidates memory overnight.
⚠ Problem this creates
Neural nets trained on new data batches overwrite old learned patterns. Catastrophic forgetting kicks in around 1–2 months of accumulated data.
Step 05
Unified
Database
The graph.db stores a relevance_score on every node. Score decays over time if unused. The same score that governs memory replay now also drives the pruning mask — one database, two jobs. No separate calibration pass needed.
✓ Resolution
Bridge the gap between graph nodes (semantic concepts) and model components (attention heads) using a static domain_to_heads lookup table built once at setup. Pruning is then a DB read + table lookup — no inference needed during the pruning step itself.
04 — Final Resolution: Controlled Learning + Unified Pruning
LOW LR + FEW EPOCHS
After 2 months, new data is ~1–2% of total accumulated knowledge. A tiny LR nudges the model gently — old weights dominate by sheer mass. 1–2 epochs max prevents overfitting to recent behavior.
GRAPH SCORE → PRUNING MASK
The same graph.db that drives memory also drives pruning. Score ≥ 7 → protect those heads. Score ≤ 3 → flag for removal. The lookup table maps domain → head_ids. Pruning is a DB read, not an inference job.
Result: Three systems protecting the model — the graph preserves structural memory, controlled training preserves pattern memory, and personal graph scores ensure the sparse subnetwork is shaped around your actual work. All three are necessary. None is sufficient alone.

Sparse Personalized Model

One Database.
Two Jobs.

The personal graph doesn't just remember you — it decides which parts of the model survive. Graph memory and model pruning share a single data structure. One relevance_score per node, governing both.

01 — The Unified Node Structure

Every node in graph.db carries a relevance_score. This score is computed from real usage — not manually assigned. It decays naturally when a concept goes unused and spikes when it becomes active again.

# every graph node looks like this node = { "concept": "pytest", "domain": "Engineering", "edges": ["python", "fastapi", "vscode"], "last_seen": 1748940000, "frequency": 0.42, "connections": 7, "bridge_value": 0.3, # ← the new field. governs both memory + pruning "relevance_score": 8.7 }

The score is a normalized composite of four signals. Each one is independently meaningful; together they capture how central a concept is to your actual working life.

# score computation def compute_score(node): freq = node["frequency"] * 3.0 # how often you use it recency = decay(node["last_seen"]) * 3.0 # how recently you used it conns = log(node["connections"]) * 2.0 # how connected it is in the graph bridge = node["bridge_value"] * 2.0 # does it link different domains? return normalize(freq + recency + conns + bridge) # → 0.0 to 10.0

The same score that governs memory replay priority in the graph also determines which attention heads survive in the model. No separate calibration process. No additional inference pass. Just a DB read.

03 — The Bridge: domain_to_heads Lookup Table

Graph nodes are semantic concepts. Model components are attention heads. These are different spaces. The bridge is a static lookup table built once at setup by probing the model with representative inputs per domain. After that, pruning is just a table lookup — no inference needed at prune time.

domain_to_heads.json — built once at setup, never changes layer · head_id pairs
# built once at install via model probing domain_to_heads = { "Engineering": [(4,2), (7,5), (12,1), (19,8)], "Research": [(3,0), (9,3), (15,6)], "System": [(2,1), (6,4), (11,0)], "Meetings": [(1,3), (5,7), (8,2)], # ... all 10 domains } # at prune time — no inference, just reads for node in graph.get_all_nodes(): score = node["relevance_score"] heads = domain_to_heads[node["domain"]] if score < 3: prune_mask.flag(heads) elif score >= 7: prune_mask.protect(heads)
04 — The Lottery Ticket Hypothesis
What LTH says
Frankle & Carlin (2019) showed that within any large randomly-initialized neural network, there exist small sparse subnetworks — "winning tickets" — that, when trained from scratch with the same initialization, can match the performance of the full network.
The key insight
The winning ticket is not smaller because it lost capacity. It's smaller because it never needed the rest of the network for the tasks it was trained on. The pruned weights were lottery losers from the start.
What NeuroPACA adds
Standard LTH finds winning tickets by iterative magnitude pruning — prune smallest weights, retrain, repeat. This finds a general winning ticket for the training distribution. NeuroPACA finds a personal winning ticket — the subnetwork that wins for your specific task distribution.
Standard LTH
Prune by weight magnitude → retrain → repeat. Finds ticket that's good for the pretraining corpus. Generic.
NeuroPACA LTH
Prune by graph relevance_score → no retraining needed. Finds ticket that's good for your actual work. Personal.
The graph score doesn't arbitrarily remove weights. It removes weights that correspond to tasks you demonstrably don't do — which is exactly what LTH says you can safely prune. Your personal data IS the ticket selection criterion.
